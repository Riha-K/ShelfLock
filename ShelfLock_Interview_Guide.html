01

From zero — the grocery problem

One carton of milk left. Two phones tap Pay at the same time. If both see qty=1, both think they bought it. ShelfLock holds the unit for a few seconds while payment finishes. If payment never comes, the hold expires and the milk goes back on the shelf.

Catalog

The list of products (SKU + name). Example: MILK-1L. Catalog is not the count. It is “what we sell.”

Stock

How many units sit at a location (store or warehouse). Same SKU can exist in both places.

Hold / reserve

We subtract from stock now and remember “this qty belongs to checkout #17 until time T.” Nobody else can take those units.

Pay / commit

Payment succeeded. Hold becomes a paid order. Stock stays down. That sale is final.

Expire / release

Payment did not happen in time. Hold dies. Qty is added back to stock.

SKU

Stock-keeping unit. The product id. All inventory math is per SKU + location.

Why not just UPDATE stock at the end? Between “add to cart” and “pay,” another buyer can take the last unit. The hold is the lock in business language. SELECT … FOR UPDATE is the lock in database language.

05

Reserve, pay, expire — SQL you must recite

Reserve (hot path)

BEGIN SELECT qty FROM stock WHERE sku=$1 AND location_id=$2 FOR UPDATE; -- lock this row until COMMIT -- if qty < requested: ROLLBACK UPDATE stock SET qty = qty - $n WHERE sku=$1 AND location_id=$2; INSERT INTO holds (..., status,'reserved', expires_at=NOW()+ttl) RETURNING hold_id; COMMIT

Other transactions that want the same milk row wait on FOR UPDATE. They will see the new qty after we commit. That is how two checkouts do not both decrement from 1 to 0 independently.

Pay

Lock the hold row. If status is still reserved, set it committed, insert orders with state paid. Stock was already reduced at reserve — do not reduce again.

Expire / release

If hold is still reserved: set status expired (or released), stock.qty += hold.qty, write an orders row for audit. If pay already committed, this function returns false and does nothing. That is how a late timer does not undo a paid sale.

Demo in main.cpp (TTL = 3 seconds)

Metrics should show reserved=3, committed=2, expired=1 (if stock was enough). Then restock prints SKUs whose on-hand is below paid-demand + 4.

06

Two locks — do not mix them up

C++ mutex on PGconn

libpq’s connection object is not thread-safe. One PGconn, many checkout threads → mutex around every query. This lock does not protect inventory by itself. It only protects the client library.

Postgres row lock

FOR UPDATE is the correctness lock. Even if two different processes (two app servers) hit the same SKU, the database serialises those transactions.

Interview gold: “If I only used a mutex, two machines would still double-spend. If I only used FOR UPDATE but shared one PGconn without a mutex, libpq could corrupt packets. I need both, for different reasons.”
07

Min-heap expiry thread

A hold has a deadline. Scanning the DB every second works but is wasteful. We push (expiry_time, hold_id) into a min-heap. One worker thread sleeps until the soonest deadline.

Why a heap

Need the earliest expiry next. priority_queue with greater is a min-heap. Push is O(log n). Peek min is O(1).

condition_variable

If the heap is empty, wait. If a new hold expires sooner than the current top, wake and reschedule wait_until.

Stale entries

Paid holds stay in the heap until their old time. When the timer fires, release sees status ≠ reserved and returns false. Harmless no-op.

steady_clock

Monotonic clock for “sleep 3 seconds.” Wall clock can jump. Expiry in SQL still uses NOW()+interval for the row.

08

OOP — only what the code really does

Repository

InventoryRepository is the only file that talks SQL. Service does not embed queries. That is the repository pattern: swap the DB without rewriting checkout logic.

Strategy

StoreFirstStrategy vs WarehouseStrategy. Same pick(options) interface. Demo uses store-first: prefer store-wadsa if it has qty.

Factory

OrderStateFactory::create("paid") returns a small state object whose name() we log. It is a real factory, not a full State-machine with transitions in the classes.

If they push on factory: “States are used for logging/metrics naming. Transitions live in SQL (reserved → committed/expired). I would put transition methods on the state objects if the workflow grew.” That is honest and better than overselling.

Demand restock — not ML

target = paid_qty_for_sku + 4. If on-hand < target, suggest the difference. It uses order history. Call it a heuristic, not a forecast model.

Honesty — resume vs code

Resume is true: catalog/stock in Postgres, transactions, row locks, indexes; reserve then pay/commit or release; threads, mutexes, min-heap for hold expiry; repository, store-versus-warehouse, order-state factory; logging, metrics, demand-based restock.

Do not add: “tests for double-buy / last unit / stock=0” — those unit tests are not in the repo. The mechanism (FOR UPDATE) is. The demo is not a formal test suite.

Do not call restock ML. It is paid-qty + 4 cover units.

Tesco angle

Retail checkout, catalog, DBMS, LLD patterns, logging. Speak SQL and OOP first.

Pace angle

This is project #3. Lead with threads, mutex, heap, why row lock ≠ mutex. Then say grocery is the domain, not the point.

12

Likely questions

Q: Walk me through ShelfLock.
Pitch. Draw products/stock/holds/orders. Recite reserve SQL. Heap expires unpaid holds. Demo: 2 pay, 1 expire.
Q: What does FOR UPDATE do?
Locks the selected row until the transaction ends. Other transactions that want that row for update block. Prevents lost updates on qty.
Q: Isolation level?
I did not set one, so Postgres default READ COMMITTED. FOR UPDATE still serialises writers on that row. I would mention SERIALIZABLE only if we needed to lock a predicate of many rows.
Q: Why decrement stock at reserve, not at pay?
So the unit cannot be reserved by someone else during payment. Cost: abandoned carts need expiry to put stock back.
Q: Mutex vs row lock?
Mutex = one PGconn. Row lock = inventory truth across processes.
Q: What if pay and expire race?
Both take FOR UPDATE on the hold. One wins. If pay commits first, expire sees status≠reserved and no-ops. If expire wins, pay no-ops. No double restore.
Q: Why a heap not a sleep(ttl) per hold?
One thread per hold does not scale. One worker + min-heap of deadlines does.
Q: Is restock machine learning?
No. Sum of paid qty plus a cover of 4 units compared to on-hand.
Q: How is this different from MatchBook?
MatchBook never hits a disk on the hot path. ShelfLock must, because inventory is shared durable state. Threads here are checkout + timer, not matching.
13

If they ask “what next?”

Connection pool

One PGconn + mutex is a bottleneck. Pool = one connection per worker, still FOR UPDATE in DB.

Tests

Two threads, stock=1, assert only one commit. Zero stock reserve fails. Expire after pay is no-op.

Heap cleanup

Remove paid ids so the timer does not wake for dead holds.
